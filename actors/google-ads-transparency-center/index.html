Competitor ads monitor: schedule it, track Google's result window

Use a daily run to return only creative IDs the watchlist has not observed before, delivered to Slack or email. Prefer advertiser IDs over domains once you identify the right accounts: they avoid reseller/affiliate ads that happen to link to the same domain. Three steps, no code:

  1. Create a task from this actor with the input below. Replace the advertiser IDs and give the watchlist a unique monitorStoreName. Run it once; that first run seeds the list, so do not treat its returned rows as changes.
  2. Schedule it: in the task, open Schedule (or Console → Schedules) and pick daily. Each run charges only creative IDs not previously observed in the capped result window; a quiet day costs a few requests and no result-event charges.
  3. Alerts: in the task's Integrations tab add Slack or Gmail on "run succeeded". Use the run's status message as the notification text; in monitor mode it reports newly observed result-window ads or that none were observed. Slack message template (Handlebars):

*Google Ads monitor:* {{resource.statusMessage}} <https://console.apify.com/storage/datasets/{{resource.defaultDatasetId}}|Open the newly observed ads>

For "only notify when there is something new", route the run through n8n / Make / Zapier (Apify triggers exist for all three) and filter on the dataset item count.

Each newly observed row carries is_new: true, first_seen_by_monitor, the creative preview URL, format, first/last shown and (with includeDetails) served countries and surfaces. This means newly observed, not necessarily newly launched. Google's capped top-N result window can reorder between runs, so a creative first shown months or years ago can enter the window and appear for the first time. Use first_shown to identify likely launches; narrow by advertiser ID, region, format, surface or date to make the window more stable. Use one monitorStoreName per watchlist.

What it costs at scale: 50 newly observed ads/day with details = 50 × $0.004 = $0.20/day, ~$6/month; without details, $1.50/month. Result-window reordering can increase this count on broad or heavily capped queries.

How often each detail field is actually populated. Measured over 225 enriched rows across 9 US/EU retail domains, so treat the thin numbers as indicative rather than exact:

field fill what you get

variations (more than one rendering) 84% Every rendering of the creative, where basic mode exposes a single preview_url.
customer_name 72% Was byte-identical to advertiser_name in every populated sample, so it is now dropped when it duplicates that column and kept only when it genuinely differs.
targeting 18% Not usable as shipped. age/gender/geo are always null and are no longer emitted; what remains is categories, which comes back as undecoded protobuf keys, as shown above.

served_countries, us_reach, details.first_shown, details.days_shown 0% Google does not return these; first_shown and days_shown are already at the top level at 100%.

Fields Google never populates are omitted from details rather than emitted as nulls, so a key's presence means it carries data. If Google starts returning any of them, they pass straight through again.

If you are researching a US-only brand, expect zero impression data and a one-element country list — allbirds.com, bombas.com and casper.com all returned 0% impressions. EU-serving advertisers do much better (56% of Nike's ads carried impressions). Enable details for country coverage and creative variations; do not buy it for targeting or category.

preview_url is not a stable key: Google randomises two query parameters on every response, so the same ad yields a different preview_url run over run (43% of rows in a back-to-back comparison). Use creative_id to dedupe or diff.

Impression and spend ranges are only published by Google for EU-served ads and political ads; elsewhere they are null. Where they exist they are lifted to the top level as impressions_low / impressions_high (global) and eu_impressions_low / eu_impressions_high (EU reach from the details block), so CSV exports and the Overview table show them without digging into details. matched_total is Google's estimate of how many ads match the whole query (useful even when you cap maxAdsPerQuery).

The field is absent when the "no" is solid: sqlite.org returns no hint, hims.com returns the one above. Filter your export on the presence of hint to pull exactly the rows worth a second look.

Advertiser-check rows for a domain

Each advertiser row for a domain carries the advertiser's billing country from its Transparency Center profile — the single most useful field for telling the domain owner apart from affiliates and resellers — plus its own ad count for that domain (creatives_count_low / creatives_count_high), the unverified flag, and the domain-wide total in domain_creatives_count_low / domain_creatives_count_high. (legal_name is also returned, but in our samples it was always identical to advertiser_name.) This distinguishes the domain owner from resellers and affiliates that also link to the domain: a nike.com check returns Nike Retail BV at 90,000–100,000 creatives, Nike, Inc. at 8,000–9,000 and a Singapore branch at 1,000–2,000, against a domain-wide 100,000–200,000. Costs 2 extra requests per advertiser row; maxAdvertisersPerQuery caps it. Candidates are ranked by how many of the domain's sampled ads each advertiser owns before that cap is applied, so truncating drops the smallest affiliates rather than the owner, and the returned rows are ordered by each advertiser's true ad count for the domain. Google's own ordering is by most recent ad, which put a one-ad affiliate ahead of the owner on ~20% of domains in a narrow region (casper.com and awaytravel.com under region: DE both did); ranking by sample share fixes both of those cases. It is still a heuristic on a 40-ad sample — use country and the creative counts to confirm the owner, and keep maxAdvertisersPerQuery above 1 when the domain may have several legitimate advertisers.

What counts as a billable row. Rows carrying data are charged, including rows with is_advertising: false — a verified "this domain has no ads in Google's index" is a result you asked for. Failed targets are not charged: a target that errored or was blocked mid-run still gets a row with an error field so the failure is auditable, but that row is written to the dataset with no charge event attached and costs you nothing. A run where every target is blocked fails outright and charges nothing at all. The run's status message reports how many error rows went out free.

In advertisers mode the unit you buy is a row, but the unit you think in is a domain — and they are not the same. A domain that advertises returns up to maxAdvertisersPerQuery rows; a domain with no ads returns exactly one. Measured over a 100-domain run: 1.63 rows per domain, so budget about $0.0033 per domain checked, not $0.002 (a 20-domain run with a higher share of non-advertisers came in at 1.35). Set maxAdvertisersPerQuery: 1 to pin it to exactly one row and $0.002 per domain, at the cost of missing co-advertisers — the single row you keep is now the advertiser with the largest share of the domain's sampled ads, which is the owner in every case we have measured, but it is a sample-based heuristic, not a guarantee.

Limits and notes

  • Google paginates to roughly 1,000 ads per query. Split large advertisers by format, surface or date range to get more.
  • Google keeps about 12 months of ad history.
  • A domain search returns every advertiser whose ads link to that domain, not only the domain owner. That can include resellers, affiliates and demo/test ads (example.com yields real ads from unrelated advertisers). Use advertisers mode to see who they are, or advertiserIds to pin one account. The reverse also happens: a third party linking to a domain makes that domain look like an advertiser (irs.gov and weather.gov both return is_advertising: true), so read the result as "ads point at this domain", not "this company buys ads".
  • is_advertising: false means no creative in Google's index is associated with that domain, which is not the same as "this company runs no Google ads". Display/image-only advertisers frequently expose no landing domain, so they are invisible to a domain query: hims.com returns false while the advertiser "Hims, Inc." is live with current image creatives. The actor now checks this for you: when a domain matches nothing, it makes one extra suggestion lookup, and if Google's index knows the domain or a matching advertiser you get a hint field on the row and the same text in the run's status message, naming the advertiser ID to retry with. No hint means Google's index knows nothing either, so the empty result is a genuine "no". The lookup costs one request and only happens on the empty path; it is skipped in onlyNewAds monitor runs, where an empty result is the normal outcome.
  • Brand-name queries are resolved through Google's own suggestion index; the largest exact/prefix match is used first. Use advertiserIds for precision.
  • Ad-text (keyword) search is only available for political ads in Google's data and is not exposed here.
  • Google rate-limits by IP. Keep the default Apify proxy on for anything beyond a few hundred ads; the actor rotates sessions on every rate-limit response and backs off, so runs complete instead of failing.
  • If Google blocks every request (bot-check page or HTTP 429 after retries), the run fails with a clear error and nothing is charged. Enable Apify Proxy (residential) or raise requestDelaySeconds. If only some targets are blocked, the run succeeds and those targets get a row with an error field — those rows are not charged.
  • Rows whose detail lookup failed (details_error) are charged at the base ad rate, not the enriched rate.
  • Monitor state is per monitorStoreName (a named key-value store in your account). Do not run two monitor runs against the same store at the same time; use one store per watchlist or schedule.
